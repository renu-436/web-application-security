# CSRF (Cross-Site Request Forgery)

## 1. Introduction

Cross-Site Request Forgery (CSRF) is a web application security vulnerability in which an attacker tricks an authenticated user into performing an unwanted action on a trusted website.

The attack takes advantage of the fact that browsers automatically send authentication cookies with requests to a website.

## 4. What is CSRF?

CSRF stands for **Cross-Site Request Forgery**.

It occurs when an attacker causes a victim's browser to send an unauthorized request to a web application where the victim is already authenticated.

For example, if a website allows a logged-in user to change their password through a request such as:

```text
/DVWA/vulnerabilities/csrf/?password_new=NewPassword&password_conf=NewPassword&Change=Change
```

and the application does not verify whether the request was intentionally made by the user, an attacker may attempt to cause the victim's browser to send such a request.

---

## 5. How CSRF Works

A typical CSRF attack involves the following steps:

1. The victim logs into a vulnerable website.
2. The website creates an authenticated session.
3. The victim's browser stores the session cookie.
4. The attacker creates a malicious request.
5. The victim is tricked into sending or triggering the request.
6. The browser automatically includes the authentication cookie.
7. The vulnerable server accepts the request as if it came from the victim.

### Basic Flow

```text
Victim logs in
      ↓
Authenticated session created
      ↓
Attacker prepares malicious request
      ↓
Victim triggers the request
      ↓
Browser sends authentication cookie
      ↓
Server processes the request
```

## 7. Example Vulnerable Request

A vulnerable request may have a structure similar to:

```http
GET /DVWA/vulnerabilities/csrf/?password_new=NewPassword&password_conf=NewPassword&Change=Change HTTP/1.1
Host: localhost
```

The important point is that the request contains the password parameters but does not contain a unique CSRF token.

---

## 8. CSRF Token

A **CSRF token** is a random, unpredictable value generated by the server and associated with the user's session.

The token is included with a legitimate request.

Example:

```text
password_new=NewPassword
password_conf=NewPassword
Change=Change
user_token=RANDOM_TOKEN_VALUE
```

The server verifies the token before processing the request.

If the token is missing or incorrect, the server rejects the request.

---

## 9. Why CSRF Tokens Prevent CSRF

An attacker generally cannot know the victim's unique CSRF token.

Therefore, even if the attacker can cause the victim's browser to send a request, the attacker cannot normally construct a valid request containing the correct token.

### Protected Request Flow

```text
User submits request
       ↓
CSRF token included
       ↓
Server validates token
       ↓
Token valid?
   ↓          ↓
 YES          NO
  ↓            ↓
Process       Reject
request       request
```

## 10. Other CSRF Protection Methods

### 10.1 SameSite Cookies

The `SameSite` cookie attribute can restrict when cookies are sent with cross-site requests.

Example:

```http
Set-Cookie: session=abc123; SameSite=Lax; Secure; HttpOnly
```

Common SameSite values include:

- Strict
- Lax
- None

---

### 10.2 Origin Header Validation

The server can check the `Origin` header to determine whether a request originated from an allowed website.

Example:

```http
Origin: https://example.com
```

The application can reject requests from unexpected origins.

---

### 10.3 Referer Validation

Applications can also check the `Referer` header as an additional validation mechanism.

However, it should not necessarily be treated as the only CSRF defense.

---

### 10.4 Secure Application Design

State-changing operations should use appropriate HTTP methods and require proper authorization and request validation.

## 12. Security Analysis

A CSRF-vulnerable application may accept a state-changing request based only on the user's authenticated session.

The key security issue is the lack of verification that the request was intentionally generated by the legitimate user.

A CSRF token provides an additional verification value that an attacker should not be able to predict.

---

## 13. Prevention

Recommended CSRF protections include:

- Use unpredictable CSRF tokens.
- Validate the token on every relevant state-changing request.
- Use `SameSite` cookie protections.
- Validate the `Origin` header where appropriate.
- Use secure session management.
- Require authentication and authorization checks.
- Avoid relying on a single defensive mechanism when multiple layers are practical.

## 16. Conclusion

CSRF is a web application vulnerability that can cause authenticated users to perform unintended actions.

This task provided an understanding of how CSRF attacks work, why authentication cookies alone are not sufficient to distinguish legitimate requests from forged requests, and how CSRF tokens and additional security controls can protect state-changing operations.
